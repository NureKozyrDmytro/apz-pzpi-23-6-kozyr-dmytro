3.2 Опис прийнятих інженерних рішень
У межах лабораторної роботи було розроблено web-застосунок для системи CargoGuard. Його створено як клієнтську частину, що працює з уже реалізованим backend API. Основне призначення web-застосунку - надати користувачам зручний браузерний інтерфейс для роботи з вантажами, контейнерами, перевезеннями, телеметрією, інцидентами та журналом подій.
CargoGuard використовується для контролю перевезення цінних вантажів у контейнерах. Серверна частина приймає телеметрію від IoT-модуля, зберігає дані у PostgreSQL, перевіряє показники температури та вологості, а також створює інциденти у випадку порушення умов перевезення. Web-застосунок не дублює цю логіку, а надає інтерфейс для перегляду та керування даними системи.
Frontend реалізовано з використанням React, Vite та TypeScript. React було обрано через компонентний підхід до побудови інтерфейсу, Vite - через швидкий запуск і просту конфігурацію, а TypeScript - для кращого контролю типів при роботі з моделями даних та відповідями API.
Код web-застосунку поділено на сторінки, компоненти, API-клієнт, модуль авторизації, локалізацію, типи даних та стилі. Така структура дозволяє окремо підтримувати інтерфейс, роботу з backend API, збереження токена та переклади.
У системі використовується рольова модель доступу. Для користувача з роллю observer доступний перегляд основних даних. Користувач з роллю operator може створювати та редагувати вантажі, контейнери, перевезення, змінювати статус перевезень і вирішувати інциденти. Користувач з роллю admin додатково отримує доступ до адміністративного розділу, де можна керувати користувачами, виконувати експорт даних, створювати резервну копію та імпортувати дані для тестового відновлення.
Для автентифікації використовується JWT. Після входу користувача web-застосунок отримує токен від backend і зберігає його на стороні клієнта. Далі цей токен додається до захищених HTTP-запитів у заголовку Authorization. Остаточна перевірка прав доступу залишається на сервері, а frontend лише приховує недоступні розділи та дії залежно від ролі користувача.
У web-застосунку реалізовано підтримку двох мов інтерфейсу: української та англійської. Перемикач мови доступний у верхній частині інтерфейсу. Основні назви сторінок, кнопки, статуси, підписи полів, повідомлення та порожні стани змінюються відповідно до вибраної мови. Формат дат також залежить від локалі: для української використовується uk-UA, для англійської - англомовний формат.
Для роботи з даними було реалізовано сторінки Dashboard, Shipments, Cargo, Containers, Incidents, Event logs та Admin. Dashboard показує короткий огляд системи: кількість активних перевезень, контейнерів, активних інцидентів, останню телеметрію та останні інциденти. На сторінках Cargo, Containers і Shipments доступні форми створення та редагування записів. Для контейнерів API key відображається у скороченому вигляді, а для його використання передбачено кнопку копіювання.
Для адміністратора було додано окремі backend endpoints для експорту, імпорту та резервного копіювання даних. Експорт і backup повертають JSON-дані, які можна зберегти локально. Імпорт реалізовано як обмежений механізм для dev/testing-сценаріїв, щоб не пошкодити критичні дані користувачів та журнал подій.
3.3 Опис взаємодії компонентів web-застосунку одне з одним та з іншими елементами системи
Web-застосунок CargoGuard працює як frontend-частина системи. Користувач взаємодіє з інтерфейсом у браузері, а всі операції з даними виконуються через REST API серверної частини. Прямого доступу до бази даних frontend не має.
Після відкриття web-застосунку користувач потрапляє на сторінку входу. Він вводить email і пароль, після чого frontend надсилає запит до backend. Якщо дані правильні, сервер повертає JWT-токен і дані користувача. Після цього web-застосунок зберігає токен і завантажує інформацію, потрібну для відображення інтерфейсу.
Основним компонентом для взаємодії з сервером є API-клієнт. Він формує HTTP-запити до backend, додає токен авторизації, обробляє відповіді та передає дані сторінкам. Сторінки не звертаються до backend напряму, а використовують спільні функції API-клієнта. Завдяки цьому логіка роботи з мережею зосереджена в одному місці.
Після авторизації інтерфейс будується з урахуванням ролі користувача. Якщо користувач має роль observer, він може переглядати дані, але не бачить адміністративних дій. Для operator доступні операції створення та редагування основних сутностей системи. Для admin відображається додатковий розділ адміністрування.
На сторінці Shipments frontend отримує список перевезень, пов’язані вантажі та контейнери. Користувач може створити нове перевезення, змінити його параметри, переглянути деталі або змінити статус. Після кожної зміни web-застосунок повторно завантажує актуальні дані з backend, щоб інтерфейс відповідав поточному стану системи.
Сторінка Shipment details показує маршрут, статус, дані вантажу, контейнер, останню телеметрію та пов’язані інциденти. Дії зі статусом перевезення залежать від поточного стану: для запланованого перевезення можна виконати Start або Cancel, для активного - Complete або Cancel, а для завершених і скасованих перевезень кнопки зміни статусу не відображаються.
Сторінки Cargo та Containers використовуються для керування довідковими даними системи. Для кожного запиту створення або оновлення frontend передає тільки ті поля, які потрібні backend DTO. Це важливо, оскільки серверна частина використовує валідацію і не повинна отримувати зайві поля, наприклад id, createdAt або службові значення.
Сторінка Incidents відображає всі інциденти системи та дозволяє фільтрувати їх за статусом і критичністю. Якщо інцидент ще не вирішено, користувач з відповідною роллю може натиснути кнопку Resolve. Після цього backend оновлює інцидент, записує дату вирішення і додає відповідну дію до журналу подій.
Сторінка Event logs використовується для перегляду історії дій у системі. У журналі можна побачити створення, оновлення, зміну статусів, вирішення інцидентів, експорт, імпорт та створення резервних копій. Це допомагає відстежувати роботу користувачів і зміни в системі.
Адміністративний розділ взаємодіє з endpoints для керування користувачами, експорту, імпорту та резервного копіювання. Перед виконанням адміністративних дій backend перевіряє роль користувача. Якщо доступу недостатньо, frontend отримує помилку і відображає її користувачу.
Таким чином, frontend відповідає за інтерфейс, локалізацію, маршрутизацію, відображення даних і реакцію на дії користувача. Backend відповідає за перевірку доступу, бізнес-логіку, роботу з PostgreSQL, обробку телеметрії, створення інцидентів та збереження журналу подій.
3.4 UML діаграми
Для опису web-застосунку було підготовлено чотири UML-діаграми. Вони показують основні можливості користувачів, загальну компонентну будову системи, послідовність взаємодії web-застосунку з backend API та логічну структуру frontend-проєкту.
UML діаграма прецедентів показує основні сценарії роботи у web-застосунку CargoGuard. На діаграмі виділено основні функції користувача та адміністративні можливості. Користувач системи може увійти в систему, змінити мову інтерфейсу, переглядати Dashboard, працювати з перевезеннями, вантажами, контейнерами, інцидентами та журналом подій. Адміністратор додатково має доступ до керування користувачами, експорту даних, створення резервної копії та імпорту даних.
  

Рисунок 3.1 - UML діаграма прецедентів web-застосунку CargoGuard
UML діаграма компонентів відображає загальну будову web-застосунку та його зв’язок із серверною частиною. Web-застосунок містить сторінки інтерфейсу, функціональні модулі, спільні UI-компоненти, модуль локалізації, API-клієнт і сховище JWT-токена. Серверна частина складається з Backend REST API, модуля автентифікації та авторизації, бізнес-логіки і бази даних PostgreSQL. 
  

Рисунок 3.2 - UML діаграма компонентів web-застосунку CargoGuard


UML діаграма послідовності описує типовий сценарій обміну даними між користувачем, web-інтерфейсом, API-клієнтом frontend, backend API, модулем перевірки JWT/ролей та базою даних PostgreSQL. На діаграмі показано два варіанти виконання запиту: коли дія дозволена і коли користувач не має достатніх прав доступу. У першому випадку backend виконує запит до бази даних і повертає JSON-відповідь, у другому - повертає помилку доступу. 
  

Рисунок 3.3 - UML діаграма взаємодії web-застосунку з backend API


UML діаграма пакетів показує логічну структуру frontend-проєкту. У web-застосунку виділено пакети app, pages, features, widgets та shared. Пакет app містить маршрутизацію, основний layout і глобальні провайдери. Пакет pages містить сторінки застосунку. Пакет features об’єднує функціональні частини, пов’язані з авторизацією, перевезеннями, вантажами, контейнерами, інцидентами та адмініструванням. Пакет widgets містить елементи інтерфейсу, які повторно використовуються на різних сторінках. Пакет shared містить API-клієнт, сховище токена, локалізацію, типи даних і допоміжні стилі.
