4.2 Опис прийнятих інженерних рішень
У межах лабораторної роботи для серверної частини програмної системи CargoGuard було реалізовано горизонтальне масштабування. Горизонтальне масштабування передбачає запуск декількох однакових екземплярів backend-сервера, які виконують одну й ту саму бізнес-логіку та можуть паралельно обробляти HTTP-запити.
CargoGuard є програмною системою для контролю перевезення цінних вантажів. Backend відповідає за автентифікацію користувачів, авторизацію за ролями, роботу з вантажами, контейнерами, перевезеннями, телеметрією, інцидентами та журналом подій. Також серверна частина приймає дані від IoT-емулятора і створює інциденти, якщо умови перевезення порушують допустимі межі.
Оскільки backend системи реалізований як монолітний REST API, його не було штучно розділено на мікросервіси. Для цієї лабораторної роботи більш доцільним є запуск декількох копій одного backend-додатка. Такий підхід дозволяє показати масштабування системи без зміни основної предметної логіки та без ускладнення архітектури на рівні бізнес-функцій.
Для розподілу навантаження між backend-інстансами використовується Nginx Load Balancer. Користувач, web-застосунок, мобільний застосунок або інструмент навантажувального тестування звертається до єдиної точки входу. Після цього Nginx перенаправляє запит до одного з доступних backend-контейнерів.
Для коректного порівняння було підготовлено два сценарії запуску:
* конфігурація з одним backend-інстансом, Nginx і PostgreSQL;
* конфігурація з трьома backend-інстансами, Nginx і PostgreSQL.
В обох випадках використовується однакова зовнішня точка входу - http://localhost:8080. Це дозволяє порівнювати результати тестування в однакових умовах, оскільки в обох сценаріях є Docker, Nginx, PostgreSQL і однаковий Locust-тест. Відрізняється тільки кількість backend-інстансів.
Схема масштабованого розгортання має такий вигляд:
Користувач / Locust -> Nginx Load Balancer -> backend-1 / backend-2 / backend-3 -> PostgreSQL
Основна мета такого підходу - показати, що backend CargoGuard може працювати не лише як один серверний процес, а і як декілька екземплярів одного сервера за балансувальником навантаження. При цьому для клієнтів системи зберігається одна точка входу, а backend-інстанси працюють зі спільною базою даних.
4.3 Опис технічних рішень, які роблять масштабування можливим 
Для реалізації масштабування серверної частини було використано Docker, Docker Compose, Nginx та Locust. Backend-додаток пакується в Docker image за допомогою Dockerfile. Під час побудови image встановлюються залежності, виконується збірка TypeScript-коду та задається команда запуску сервера. Після цього з одного Docker image можна запускати декілька незалежних backend-контейнерів.
Для демонстрації масштабування було підготовлено два окремі Docker Compose-файли:


docker-compose.scale-1.yml - запуск одного backend-інстанса через Nginx;
docker-compose.scale.yml - запуск трьох backend-інстансів через Nginx.
Файл docker-compose.scale-1.yml містить PostgreSQL, контейнер для виконання міграцій, backend-1 та Nginx. У цьому сценарії Nginx проксирує всі запити тільки на backend-1:3000. Для нього використовується окремий конфігураційний файл nginx/nginx.single.conf.
Файл docker-compose.scale.yml містить PostgreSQL, контейнер для виконання міграцій, backend-1, backend-2, backend-3 та Nginx. У цьому сценарії Nginx розподіляє запити між трьома backend-контейнерами. Для нього використовується конфігурація nginx/nginx.conf, де описано upstream-групу backend-серверів.
PostgreSQL використовується як спільне сховище даних для всіх backend-інстансів. У базі даних зберігаються користувачі, вантажі, контейнери, перевезення, телеметричні записи, інциденти та журнал подій. Завдяки цьому будь-який backend-інстанс може обробити запит, звернувшись до спільної бази даних.
Окремий контейнер migrations використовується для виконання міграцій перед запуском основних backend-контейнерів. Це потрібно для того, щоб структура бази даних була підготовлена до роботи системи. Також це запобігає ситуації, коли декілька backend-інстансів одночасно намагаються виконувати міграції.
Nginx використовується як балансувальник навантаження. У сценарії з одним backend-інстансом він перенаправляє запити тільки до backend-1. У сценарії з трьома backend-інстансами він розподіляє запити між backend-1, backend-2 та backend-3 за принципом round-robin. Це означає, що послідовні запити передаються різним backend-контейнерам.
Для перевірки роботи масштабування було розширено endpoint /health. Він повертає статус сервера, назву backend-інстанса та часову мітку. Назва інстанса береться з перемінної середовища INSTANCE_ID. У конфігурації з одним backend повертається backend-1. У конфігурації з трьома backend-інстансами endpoint /health показує послідовну зміну backend-1, backend-2 та backend-3.
Також було враховано stateless-підхід до авторизації. JWT-токен передається в заголовку запиту, тому backend не повинен залежати від локальної сесії конкретного процесу. Раніше refresh tokens зберігалися в пам’яті одного backend-процесу, що погано підходить для масштабування. Для лабораторної роботи process-local сховище refresh tokens було прибрано, щоб запити користувача могли коректно оброблятися різними backend-інстансами. У production-версії для цього доцільно використовувати Redis або збереження refresh tokens у базі даних.
Таким чином, масштабування стало можливим завдяки контейнеризації backend, спільній базі PostgreSQL, запуску міграцій в окремому контейнері, використанню Nginx як балансувальника та відмові від process-local стану, який заважав би роботі декількох backend-інстансів.
4.4 Опис навантажувальних тестів з ілюстрацією зв’язку між масштабуванням і витримуваним навантаженням.
Для перевірки роботи масштабування було проведено навантажувальне тестування за допомогою Locust. Тестування виконувалося для двох сценаріїв:
* один backend-інстанс через Nginx на http://localhost:8080;
* три backend-інстанси через Nginx на http://localhost:8080.
Для обох сценаріїв використовувалися однакові параметри навантаження: 100 віртуальних користувачів, швидкість появи користувачів 20 користувачів за секунду та тривалість тесту 2 хвилини. Такий підхід дозволяє порівнювати результати між сценаріями без зміни умов навантаження.
Locust-тест виконував запити до основних endpoint-ів системи:
* GET /health;
* POST /api/auth/login;
* GET /api/shipments;
* GET /api/cargo;
* GET /api/containers;
* GET /api/incidents.
Для захищених endpoint-ів перед виконанням запитів виконувався login тестового користувача. Після цього JWT-токен додавався до наступних запитів у заголовку Authorization.
Перед навантажувальним тестуванням було перевірено роботу endpoint /health. У конфігурації з одним backend-інстансом усі відповіді надходили від backend-1. У конфігурації з трьома backend-інстансами відповіді надходили послідовно від backend-1, backend-2 та backend-3. Це підтвердило, що Nginx реально розподіляє запити між доступними backend-контейнерами.

Водночас масштабована конфігурація показала кращі значення часу відповіді. Середній час відповіді зменшився з 7 мс до 5 мс, а максимальний час відповіді зменшився з 349 мс до 242 мс. Також endpoint /health підтвердив реальний розподіл запитів між backend-1, backend-2 та backend-3. Це означає, що горизонтальне масштабування працює коректно, навіть якщо в локальному середовищі воно не дає лінійного приросту RPS.
4.5 Аналіз вузьких місць під час навантаження
Для аналізу вузьких місць під час навантаження було використано команду docker stats. Вона дозволяє переглянути використання CPU, оперативної пам’яті, мережевого обміну та операцій введення/виведення для кожного контейнера.
У сценарії з одним backend-інстансом команда docker stats показала роботу контейнерів nginx, backend-1 та postgres. Основне навантаження припадало на backend-1, оскільки всі HTTP-запити оброблялися одним серверним процесом. PostgreSQL також обробляв запити, але в межах проведеного тесту не був повністю завантажений. Це пов’язано з тим, що тест складався переважно з простих read-запитів і не створював великої кількості складних операцій запису.
У сценарії з трьома backend-інстансами навантаження розподілялося між backend-1, backend-2 та backend-3. За результатами docker stats видно, що всі три backend-контейнери працювали паралельно. Це підтверджує, що Nginx не тільки змінює instanceId у /health, а й реально передає запити різним backend-контейнерам під час навантаження.
PostgreSQL у масштабованій конфігурації залишався спільним компонентом для всіх backend-інстансів. Це означає, що при подальшому збільшенні кількості backend-контейнерів база даних може стати одним із головних вузьких місць системи. Особливо це може проявитися при масовому надходженні телеметрії від IoT-пристроїв, частому створенні інцидентів або виконанні складних запитів до журналу подій.
Nginx також є важливим елементом масштабованої конфігурації, оскільки всі зовнішні запити проходять через нього. У проведеному тесті він не став вузьким місцем, але в реальних умовах його також потрібно налаштовувати та моніторити.
Ще одним обмеженням є саме локальне середовище тестування. Backend-контейнери, Nginx, PostgreSQL, Docker Desktop і Locust працювали на одному комп’ютері. Через це результати залежать не тільки від кількості backend-інстансів, а й від CPU, оперативної пам’яті, мережевого шару Docker та роботи самого генератора навантаження.
Отримані результати показують, що горизонтальне масштабування зменшує залежність системи від одного backend-процесу і дозволяє обробляти запити декількома backend-інстансами. Водночас масштабування backend не усуває всі можливі обмеження системи. Після збільшення кількості backend-інстансів вузьке місце може зміщуватися до спільних компонентів: PostgreSQL, Nginx, Docker-хоста або генератора навантаження.
Для подальшого покращення продуктивності системи доцільно оптимізувати SQL-запити, налаштувати пул з’єднань до PostgreSQL, додати індекси для частих запитів, перевірити систему на більшому обсязі тестових даних і проводити навантажувальні тести в середовищі, наближеному до production.
Отже, у межах лабораторної роботи було реалізовано горизонтальне масштабування backend CargoGuard. Було підготовлено конфігурації для одного та трьох backend-інстансів через Nginx, проведено навантажувальне тестування за допомогою Locust і проаналізовано використання ресурсів контейнерів. Система коректно працювала в обох сценаріях, не мала помилок під час тестування, а масштабована конфігурація показала кращі значення середнього та максимального часу відповіді.
